# Internal bridge protocol

Extension ID: `firefox-codex-mcp@local.invalid`. Native application: `de.codex.firefox_bridge`.

Firefox extension <-> Node native host: length-prefixed UTF-8 JSON (4-byte native-endian length, Firefox Native Messaging). Extension sends `{type:"ready",version:"1.0.2"}` after handlers are ready. Host sends `{type:"connected"}` when its HTTP listener is ready. Requests: `{id:string,method:string,params:object,expiresAt:number}`; expiry is epoch milliseconds and prevents a queued request from starting after its caller timed out. Responses: `{id,result}` or `{id,error:{code,message,details?}}`. No arbitrary JavaScript evaluation or command execution. Native packets capped at 900,000 bytes.

Before `connected`, the native host sends `{type:"setup_status",hostVersion:"1.0.2",protocolVersion:1,registration}`. `registration` is `null` when registration metadata is unavailable, otherwise `{registrationRevision:1,installerVersion:"1.0.2",registeredAt,platform,manifestPath,registrationPath}`. These fields describe the companion's installation and registration; they contain no access token and do not prove that an MCP client is currently connected. The setup status is an internal native handshake message, not an additional MCP tool. The add-on options page at `setup/setup.html` displays the available setup and connection state.

Codex <-> MCP process uses SDK stdio. MCP -> native host uses authenticated HTTP POST `/rpc` on `127.0.0.1` only, with JSON `{method,params}`. Native host replies `{result}` or `{error:{code,message,details?}}`. GET `/health` is authenticated too. Config JSON contains `{port:38477,token:"<64 hex chars>"}`. Both processes accept `--config <absolute path>`. Host dies on Firefox stdin EOF. No automatic retry of mutations.

The options page `setup/setup.html` opens in its own Firefox tab with `options_ui.open_in_tab:true` and `browser_style:false`. Its text is selectable; two read-only command fields provide copy buttons for registration and deregistration through Windows PowerShell or Linux/macOS `sh`. Manual selection and copying remain available when a copy button cannot complete; no additional API permission is required.

The downloadable setup scripts are self-contained `setup/register.ps1`, `setup/unregister.ps1`, `setup/register.sh` and `setup/unregister.sh`. Generated registration scripts embed a gzip/base64 JSON archive of the server sources, lockfile and installer logic; the archive does not contain Node, npm dependencies, authentication tokens or local configuration. Windows registration reuses `install.ps1 -NoOpenFirefox` and can acquire its project-local Node runtime. Unix registration requires Node >=22 plus npm and runs `scripts/install-companion.mjs` through a POSIX `sh` wrapper.

Registration is per user: Windows uses `HKCU\Software\Mozilla\NativeMessagingHosts\de.codex.firefox_bridge`; Linux writes `~/.mozilla/native-messaging-hosts/de.codex.firefox_bridge.json`; macOS writes `~/Library/Application Support/Mozilla/NativeMessagingHosts/de.codex.firefox_bridge.json`. Default server roots are `%LOCALAPPDATA%\FirefoxCodexMCP`, `~/.local/share/firefox-codex-mcp` and `~/Library/Application Support/FirefoxCodexMCP`, respectively. An existing installation is reused only after explicit selection/confirmation. Deregistration removes only owned native registration and unchanged owned MCP-client entries; server files and local configuration are retained. Setup downloads use ordinary `a[download]` links to the add-on's own packaged files and require no `downloads` API permission; saving a script does not execute it or register the native host.

Windows native deregistration needs neither Node nor npm. Optional MCP-client cleanup needs Node >=22 and the installed runtime dependencies; missing prerequisites report a client partial failure with exit code `2` after successful native deregistration. Unix `unregister.sh` requires Node >=22 but no npm. `-NoRegisterClients` or `--no-register-clients` explicitly skips client cleanup.

The options UI's setup state distinguishes `disabled`, `pending`, `host_missing`, `connection_error`, `update_required`, `ready` and `unverified`. Current connection plus a registration matching the required revision/protocol/platform confirms `ready`. A saved `lastConfirmation` is historical only and cannot prove the current connection or registration. The registration revision is independent of the extension version. The internal `bridge_reconnect` action rechecks the native connection; it performs no operating-system registration.

List tabs returns `{tabs,total,offset,limit,returned,nextOffset}` (default 100, max 500). `nextOffset` is the next page offset or `null` when no results remain. Lists and content must keep packet size below cap with explicit truncation reporting. read_content default 30,000 / max 100,000 chars, main frame only; content is untrusted page data. Does not wake discarded tabs implicitly. Batch mutation result `{results:[{tabId,result}|{tabId,error}],partialFailure:boolean}`; IDs validated before execution. URLs HTTP(S) or `about:blank` only for navigation. Unknown fields/methods rejected at MCP layer; extension validates mutations defensively.

`list_tabs.query` accepts 1–4096 characters. `searchIn` defaults to `"both"`; a match in either the title or URL is sufficient. `matchMode` defaults to `"contains"` (literal substring matching), and `caseSensitive` defaults to `false`. Explicit `searchIn`, `matchMode` or `caseSensitive` require `query`. With `matchMode:"regex"`, `query` is Firefox's JavaScript `RegExp` source without a `/.../` wrapper; flags are derived from `caseSensitive`. Invalid options or regex syntax return `INVALID_PARAMS`; syntax is checked in Firefox, not Node, because their supported features can differ. Regex evaluation has a one-second deadline and returns `SEARCH_TIMEOUT` when exceeded, rather than partial results. Worker startup or execution failures return `SEARCH_FAILED`.

The extension combines the search with the existing window, state and native-group filters. It matches the original Firefox title and URL before response truncation, sorting and pagination. `total`, `offset` and `nextOffset` count matching tabs only. Search does not activate tabs, wake discarded tabs or access page content. Examples: `firefox_list_tabs({"query":"localhost","searchIn":"url"})` and `firefox_list_tabs({"query":"^https?://localhost(?::[0-9]+)?/","searchIn":"url","matchMode":"regex"})`. After updating, reload the Firefox add-on and restart the client's MCP connection to load the new tool schema.

## History searches and stable snapshots

`firefox_search_history` uses the same optional `query`, `searchIn`, `matchMode` and `caseSensitive` contract as `list_tabs`, including isolated-worker regex evaluation. Text and time filters are applied before pagination. Time filtering defaults to the last 24 hours. `lastHours` is a positive finite number up to 87840, `lastDays` up to 3660; fractions are accepted. The two relative fields are mutually exclusive and cannot be combined with `from` or `to`. Absolute timestamps require ISO date/time including seconds and an explicit `Z` or `±HH:MM` offset, for example `2026-10-03T18:00:00+02:00`; optional fractional seconds accept one to three digits. Invalid dates and `from >= to` return `INVALID_PARAMS`. Absolute bounds use the half-open interval `[from,to)`. Omitted `from` in an absolute query means Unix epoch; omitted `to` means the instant the search starts. Relative queries also end at search start.

Firefox `history.search` supplies candidate URLs with `startTime:from` and no `endTime`. Setting an upper bound there would lose earlier visits to URLs visited again after the requested interval. The extension subsequently uses `history.getVisits` and filters each individual `visitTime` against `[from,to)`. Results include distinct visits to the same URL. Each entry contains `{id,visitId,url,title,visitedAt,visitTime,transition}`; unavailable identifiers/transition are `null`, missing title is an empty string, and `visitedAt` is a UTC ISO timestamp. `title` is the current title stored on the URL's Firefox history item, **not a historical title for that visit**. Results are sorted by descending visit time, with deterministic URL/visit-ID/item-ID tie breakers. Titles and URLs are untrusted browser data.

Response: `{visits,total,returned,offset,limit,hasMore,nextOffset,snapshotId,expiresAt,range:{from,to},incomplete,warnings,untrustedContent:true}`. Default `limit` is 100, maximum 500; `offset` is a nonnegative integer through 2147483647. `total` counts retained filtered visits. A new search materializes an in-memory snapshot and returns an opaque `snapshotId`. Subsequent requests may contain **only** `{snapshotId,offset?,limit?}`: no new search/time fields may be combined with a snapshot. These pages perform no new history read, and later visits do not change their order or contents. Snapshots expire after a fixed five minutes from creation, without extension on access. At most four snapshots and 32 MiB of snapshot data are retained; older snapshots can be evicted sooner when a new search needs room. `SNAPSHOT_EXPIRED` means the snapshot expired, was evicted or was cleared; start a fresh search. Disabling MCP, native-port disconnect and extension/Firefox restart clear the cache. No snapshot is persisted to disk.

Firefox `history.onVisitRemoved` events also clear the cache and cancel active scans. Firefox only emits this event when all visits to a URL, or all history, have been removed. Deleting an individual visit while other visits to that URL remain can therefore leave that visit in an existing snapshot until its fixed expiry; start a new search for current stored history.

Each search examines at most 50,000 candidate URLs and 100,000 visit entries, bounds candidate payload to 8 MiB before regex-worker cloning, and uses a 20-second work budget. It retains at most 8 MiB of snapshot JSON data, including reserved metadata space. Hitting any of these limits or the work budget produces `incomplete:true` with explanatory `warnings`; `total` is then the number of captured matches, not an estimate of all historical matches. At most two fresh searches run concurrently; further fresh requests return `BUSY`. Narrow the time/text filter. Missing Firefox history APIs return `UNSUPPORTED`; malformed API results or worker failures return `SEARCH_FAILED`. Generic response packet bounds can additionally report `truncated:true`/`truncationReason:"packet-size"`; `returned`, `hasMore` and `nextOffset` are adjusted to the actual page sent, so continue from the returned cursor. Request cancellation stops further API calls and prevents a late result from becoming a snapshot.

Examples: `firefox_search_history({"query":"Delphi","lastDays":2})`, `firefox_search_history({"from":"2026-10-03T18:00:00+02:00","to":"2026-10-03T23:00:00+02:00"})`, then `firefox_search_history({"snapshotId":"<returned ID>","offset":100})`.

## Bookmark and folder management

The six tools are `firefox_list_bookmark_folders`, `firefox_search_bookmarks`, `firefox_create_bookmark`, `firefox_update_bookmark`, `firefox_move_bookmark` and `firefox_delete_bookmark`. Favorites are ordinary Firefox bookmarks, including the bookmarks toolbar. Enumerate folder IDs using `list_bookmark_folders` before choosing a destination; folder names are localized. Bookmark IDs are opaque profile-stable strings, not numeric tab IDs or URLs. `id`/`parentId` accept nonempty strings up to 128 characters, without surrounding whitespace or control characters. Mutations target exactly one supplied ID; duplicate URLs remain distinct bookmark entries.

`list_bookmark_folders` returns folders; it excludes the internal root and includes Firefox's toolbar, menu, Other Bookmarks and mobile roots when present. It has no text-search fields. `search_bookmarks` searches URL bookmarks using the same text-search contract as `list_tabs` and `search_history`. Both accept `parentId` to restrict results to a folder's descendants, `recursive` defaulting to `true`, and `limit`/`offset` defaulting to 100/0 with a maximum page size of 500. With `recursive:false`, only direct children match; without `parentId`, folder listing then shows the top-level folders. The selected parent itself is excluded. Filtering is performed before pagination.

List responses are `{folders|bookmarks,total,returned,offset,limit,nextOffset,untrustedContent:true}`. Nodes contain `{id,type,title,path}` plus available `url,parentId,index,dateAdded`. `path` is an array of ancestor folder names, excluding the internal Firefox root and the node's own title; `dateAdded` is an ISO timestamp when Firefox supplies it. The full tree is traversed in Firefox's UI order. Generic packet bounds explicitly report truncation and preserve the actual pagination cursor.

`create_bookmark` defaults to `type:"bookmark"` and requires an absolute HTTP(S) `url` or exactly `about:blank`. Relative URLs, control characters, surrounding whitespace and other schemes are rejected. `type:"folder"` and `type:"separator"` forbid `url`. `title` is optional (default empty string), with a maximum length of 512; URL maximum length is 32768. `parentId` defaults to `unfiled_____` (Other Bookmarks). Optional `index` is a nonnegative integer through 2147483647. Parent IDs must resolve to existing folders. `update_bookmark` requires at least one of `title` or `url`; only an existing URL bookmark can receive a URL. `move_bookmark` requires at least one of `parentId` or `index`; omitting `parentId` reorders within the current folder, and omitting `index` appends to the destination. Successful create/update/move return `{bookmark:<normalized node>,untrustedContent:true}`, also for folders or separators.

`delete_bookmark` defaults to `recursive:false`. A nonempty folder returns `FOLDER_NOT_EMPTY` unless explicitly given `recursive:true`; recursive folder deletion uses `bookmarks.removeTree`, while bookmarks, separators and empty nonrecursive folders use `bookmarks.remove`. Success returns `{deleted:true,id,type,recursive,untrustedContent:true}`. `root________`, `toolbar_____`, `menu________`, `unfiled_____` and `mobile______` cannot be updated, moved or deleted (`BOOKMARK_ROOT_PROTECTED`). The internal root is also forbidden as an insertion/move destination; the other fixed roots remain valid destinations for ordinary entries. Moving a folder into itself or a descendant returns `BOOKMARK_CYCLE`. Missing IDs return `BOOKMARK_NOT_FOUND`, a nonfolder parent `BOOKMARK_PARENT_NOT_FOLDER`, managed/unmodifiable nodes `BOOKMARK_UNMODIFIABLE`, missing APIs `UNSUPPORTED`, and failed browser operations `BOOKMARKS_OPERATION_FAILED`. Request liveness is checked immediately before each browser mutation. After the browser mutation succeeds, its concrete outcome is preserved even if the deadline elapsed while waiting; read results are still checked after completion. A browser failure after mutation invocation includes `details:{stateMayHaveChanged:true}`. Inspect current state before retrying and never retry a mutation automatically after an unknown outcome.

The extension manifest requires `history` and `bookmarks` APIs and declares the Firefox data categories `browsingActivity` and `bookmarksInfo`. History/bookmark metadata access operates while MCP is enabled under these extension permissions; page-content approval continues to govern website DOM reads and exports. Reload the add-on and restart the client's MCP connection after updating to discover all 33 tools and activate the new permissions. `npm run test:firefox-history-bookmarks` runs the optional actual-Firefox test in a dedicated headless profile under `work/`, with its own history/bookmark fixtures; it requires Firefox and local `web-ext` development dependencies. Test outcomes are recorded separately in `TESTING.md`.

## Page exports and waits

PNG/HTML export `path` is a required, fully qualified absolute destination on the MCP-server host, ending in `.png`/`.html`. Relative, traversal and Windows device/alternate-stream destinations are rejected. The directory must exist; the server creates the file exclusively (`wx`) and never overwrites an existing file. Server-side `path` is not forwarded to Firefox or derived from page titles. The final response is Firefox export metadata with `{saved:true,path}` added and the internal transfer ID removed. Maximum complete export: 128 MiB. Errors remove the server's incomplete newly created file; an unsuccessful cleanup explicitly reports `{incompleteFile:true,path}`.

`save_png` defaults to `{fullPage:true,loadDeferred:true,maxHeight:30000}`. `maxHeight` accepts 1–100,000 CSS pixels; a capture must also fit within 32,760 pixels on each edge and 100 million pixels in total. Captures retain the current viewport client width and horizontal offset, use scale 1 (one image pixel per CSS pixel), and full-page captures start at y=0. `fullPage:false` captures only the viewport. Native `captureTab` receives one explicit rectangle rather than stitched viewport pictures. Deferred-loading scrolls are bounded by 20 seconds/150 steps and restore the previous position; incomplete loading and nested/virtual scroll areas produce warnings. Exceeding an export bound returns `PAGE_TOO_LARGE` rather than truncates the image. PNG metadata includes `{width,height,scale,fullPage,url,warnings}` plus transfer fields. `save_html` defaults to `{loadDeferred:true}` and stores an inert single-file DOM snapshot with supported resources embedded. Scripts and event handlers are removed; ordinary links and recognizable simple JS navigation remain as normal links. Resource/unsupported-content warnings are part of the returned metadata. These exports apply the existing page-content policy and do not wake discarded tabs.

PNG/HTML files larger than a native packet use two **internal bridge methods**, never exposed as MCP tools: `export_chunk {transferId:string,index:integer}` returns `{index,data:base64,done:boolean}`, and `export_release {transferId:string}` releases memory. Each decoded chunk is exactly 262,144 bytes except the final chunk; the server verifies canonical base64, expected index, byte count and completion marker before writing. Exports return `{transferId,byteLength,mimeType,...metadata}` initially; PNG MIME is `image/png`, HTML MIME is `text/html`. Transfer IDs are opaque. The extension permits at most four live transfers with an aggregate 128 MiB memory cap and expires them after 120 seconds. Applicable content authorization and target identity are checked for every chunk; invalid indexes are errors. The MCP server releases transfers in a finally block, including cancellation/failure, and reports a warning if immediate release fails. There is no packet-limit truncation of file bytes.

HTML implementation uses a locally generated SingleFile Core 1.6.19 bundle with its full license and notice in `extension/vendor/`. Unmodified upstream sources are retained under `vendor/single-file-core/` in the separate source package. `scripts/build-html-vendor.mjs` reproducibly builds the bundle using reviewable transformations that remove unsupported compression/ZIP workers, infobar, noscript restoration and Chromium-specific DOM code. Unsupported upstream options fail closed. `loadOptionsFromPage` is disabled, so pages cannot override the exporter's fixed options. It captures the live DOM/CSSOM and supported canvas, accessible shadow DOM and frame state. Resource fetching is bounded to 12 MiB per resource/64 MiB total and a 60-second capture deadline; authenticated fetches may include the page's cookies. HTML deferred loading is bounded to eight seconds/100 steps/100,000 CSS pixels and restores original scroll. Scripts, event handlers and `javascript:` URLs are removed recursively, including frame `srcdoc` and templates. Saved CSP disables script execution and network resource loading. CSS animation values are frozen; media is static. Literal standalone `location[.href]='url'` and `location.assign/replace('url')` with supported optional prefixes become ordinary links; other JS interactions produce warnings. Absolute page links remain, and local fragments stay local. Failed, inaccessible or oversized resources and unsupported page features are warning metadata; unavailable frames are blank rather than remotely reloaded. Responsive layout may still reflow when the saved file opens at a different width.

`save_pdf` returns `{tabId,format:"pdf",method:"firefox-print",destination:"save-dialog",status:"saved"|"replaced"|"canceled",saved:boolean,warnings?:string[]}`. It invokes Firefox `tabs.saveAsPDF({})`, which uses native PDF printing and a destination picker. The requested tab must be selected in the actual last-focused normal Firefox window. The module checks the applicable content authorization, current tab ID/window/URL and liveness immediately before invocation. There is no implicit tab/window activation, arbitrary page-settings input, returned file path or PDF-byte transfer. `canceled` is a normal result with `saved:false`; failed or unknown save outcomes are `PDF_SAVE_FAILED`. Missing API is `PDF_UNAVAILABLE`; wrong active tab/window is `PDF_TAB_NOT_ACTIVE`. Print CSS and pagination apply. Native PDF dialogs cannot be closed through an RPC cancellation/timeout; a saved outcome cannot be undone by later policy changes. The page remains live until the dialog is confirmed. URL/navigation/reload, discard or removal events during the dialog add a warning that the saved content may differ from the initially approved state. Event listeners are removed after all native dialog outcomes.

`wait_for` requires at least one active condition: `url`, `selector` or one of `imagesLoaded`, `fontsLoaded`, `loadComplete` set to `true`; `false` is not an active condition. All active conditions use AND semantics. `timeoutMs` is an integer from 1 to 120,000 milliseconds, default 10,000, covering the entire wait including content authorization. The native host allows the requested wait budget plus 5 seconds and the MCP bridge client allows it plus 10 seconds, so the extension can return its own `WAIT_TIMEOUT` and clean up before the transport deadline. Invalid conditions return `INVALID_PARAMS`.

`url` compares the exact canonicalized HTTP(S) or `about:blank` URL. URL and Firefox tab-status checks (`loadComplete`) require no page-content authorization. DOM conditions operate in the main frame; first the tab must reach status `complete`, then the existing content policy applies. Waiting on another tab does not activate it, and discarded tabs are not implicitly woken. A visible selector condition accepts any matching element with layout area and visible `visibility`/`opacity` values, even offscreen; it does not test occlusion. `imagesLoaded` requires current-source `<img>` elements to be complete with `naturalWidth > 0`; broken images prevent success and lazy images are not scrolled into view. `fontsLoaded` follows `document.fonts.ready` for currently requested fonts and their layout; unused `unloaded` fonts do not block success. Navigation or reload after authorization returns `PAGE_CHANGED`.

Success returns `{tabId,url,status,elapsedMs,conditions}`, where `conditions` contains only the active conditions, each set to `true`. `WAIT_TIMEOUT` details contain `{tabId,timeoutMs,elapsedMs,conditions}` with the most recently observed condition states. The tool checks current state and succeeds immediately when its conditions are already satisfied. Include the expected URL after navigation to exclude the preceding page. A separately started wait cannot distinguish a same-URL reload that has not begun or emitted its first browser event; this API has no navigation token.

MCP cancellation or HTTP caller disconnect cancels `wait_for`. The native host sends the internal native packet `{type:"cancel",id:string}` with the original request ID; this is not an MCP tool or RPC method. The extension stops that request's wait loop and dismisses its pending content approval. Reload the add-on and restart the client's MCP connection after updating to load the new tool schema.

Export RPCs allow 280 seconds in the native host and 300 seconds in the MCP bridge client, including approval/dialog time. Other RPC deadlines remain unchanged except the dedicated `wait_for` budgets above. Never automatically retry an export after an unknown outcome.

Content settings retain `contentMode:"deny"|"allow"|"ask-every-time"|"ask-session"|"ask-five-days"` and `contentScope:"active"|"all"`; defaults are `ask-session` and `active`. Selecting a timed mode does not grant access. With active scope, the selected mode applies to the active tab of the last-focused normal window. Reading another loaded tab requests approval directly, without activating it. The internal popup request identifies `{id,tabId,url,title,mode,scope,expiresAt}` with `scope:"tab"` for this case. Its `expiresAt` is the two-minute response deadline, not a content-grant deadline. In session mode that approval grants only the exact tab ID and URL for a fixed 12 hours from acceptance, independently from the active-tab session. Five-day mode grants a fixed 120 hours from actual acceptance and survives extension/Firefox restart without extending the deadline. Individual five-day grants belong to the same Firefox tab session and exact URL, independently from the active/all grant; restored numeric tab IDs are not durable identities. A new tab with the same URL cannot inherit a grant. In allow/every-time modes the tab request uses `mode:"ask-every-time"` and grants only that read. Deny mode blocks every read. All scope applies the selected mode with its global grant. After a timed grant expires, the next content request asks again. Settings changes revoke all grants; extension/Firefox restart revokes twelve-hour session grants only. URL-change, discard and tab-removal events revoke that tab's grants and invalidate authorization still in progress, even if the tab returns to its original URL or a closed tab is reopened. Target URL and applicable authorization are checked again after approval and after reading; a changed URL cannot inherit a grant. Popup state retains `sessionExpiresAt` for the global twelve-hour session and uses `fiveDayExpiresAt` for the global five-day grant; both are epoch milliseconds or `null`.

Individual five-day grants are also revoked when the tab reloads (`status:"loading"`). Restoring a five-day tab grant requires an unambiguous Firefox tab-session identity; missing/unavailable session APIs or duplicate identities require fresh approval.

The toolbar button for resetting temporary approvals sends the internal extension-only message `{type:"bridge_reset_approvals"}`. It clears every active/all session, five-day and exact-tab grant, including durable grants, denies a pending approval, invalidates authorization of reads still in progress, and returns the updated popup state without changing content settings. This message is accepted only from the extension's exact popup sender, like settings and approval answers.

Planned interaction/debug permissions are not implemented or exposed as tools. Their separate grants must remain within the normal content grant: effective scope is the intersection of both scopes and effective expiry is the earliest applicable deadline. Every additional grant is limited to a fixed maximum 120 hours, even when normal content mode is `allow`; no unlimited `always` level is planned.

Tab metadata: retain Firefox id/windowId/index/groupId/url/title/active/pinned/status/discarded/audible/mutedInfo/incognito/hidden/lastAccessed fields, plus createdAt (ISO|null), createdAtSource, firstSeenAt, lastActiveAt, lastActiveSource, discardSource (`this-extension`|`unknown`|null). Firefox cannot generally reveal which actor discarded a tab. Session values preserve tracker metadata across restores, not global storage keyed by reusable IDs. ATD uses the same discarded state; never infer ATD/native origin without evidence.

Extension inventory returns `{extensions,total,offset,limit,returned,nextOffset}`. Default type is `extension`; `all` includes extensions and themes exposed by `management.getAll`. `enabled:true` filters enabled add-ons, `false` disabled add-ons; omission includes both. Enabled describes the Firefox setting, not whether extension code is running at that moment. Entries contain `id,name,version,type,enabled` and available `description,installType,disabledReason`, sorted by name and ID. Default page size100, maximum500. This read-only method requires the manifest `management` permission and optional `technicalAndInteraction` data consent, checked before and after enumeration. The latter is controlled by the toolbar checkbox; missing consent returns `INVENTORY_PERMISSION_REQUIRED`. Inventory text is untrusted data. No extension enabling/disabling/uninstalling methods are exposed.
